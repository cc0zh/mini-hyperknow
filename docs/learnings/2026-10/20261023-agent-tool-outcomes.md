# 工具结果未知，为什么不能直接重试？

Agent 工具调用至少跨三道边界：模型声明意图、宿主执行副作用、宿主保存结果。进程可能在任何两步之间退出。磁盘没有成功结果，并不代表文件没写入或命令没执行。

## 从调用 ID 而不是成功提示思考

消息中的 assistant tool call 和 tool result 必须按 ID 配对。恢复时发现有 call 没有 result，只能说明“缺少可证明的结果”。安全做法是补一个明确的 interrupted／outcome unknown 结果，修复模型输入协议，但**不重新执行工具**。

这类补全是在记录不确定性，不是制造业务成功，也不能据此断定副作用不存在。继续之前应由宿主检查真实文件／事务状态；需要端到端可重试时，再为具体业务设计幂等键，而不是让通用内核猜测命令可否重复。

## 缩小窗口，而不是宣称消灭窗口

每个工具完成后立即持久化结果，再执行下一个写入，比等整批结束后回填更可靠。只读组可并行，结果按完成顺序落盘、按 ID 配对；返回列表仍可保持原请求顺序。写入之间有串行屏障，避免后一个动作先于前一个结果落盘。

但命令执行与 JSONL append 不属于同一事务，仍有不可消除的崩溃窗口。原子文件替换只保证文件不会只写一半，不能保证“文件替换＋日志提交”同时发生。把这些概念混在一起，很容易错误承诺 exactly-once。

## 预算压缩为什么也需要两阶段提交？

先选取完整旧轮次，保留最近 user turn 及其 tool calls／results；随后生成候选摘要，验证确实变小且满足预算，持久化 checkpoint 成功后才替换 active history。摘要失败不能提前清空历史。

active history 是模型当前看到的工作集，原始 JSONL 是事实来源。压缩只更换工作集，不抹去原始记录。摘要是有损推断，必须当历史数据而非新的系统授权；usage 也要区分摘要调用与主调用，缺失保持未知，不能用 Token 估算补成真实费用。

## 自检

- 如果机器在 `os.replace` 后、结果 append 前断电，你能从日志证明操作没发生吗？不能。
- 如果摘要模型失败，下一次主调用能看到压缩前历史吗？应该能，或者明确因预算停止，而不是收到空历史。
- 如果并行结果乱序到达，如何恢复配对？用稳定调用 ID，而不是依赖相邻数组位置。
