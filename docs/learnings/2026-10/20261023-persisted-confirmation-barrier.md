# 等待确认是一份业务事实，不是一个阻塞中的函数

## 为什么值得单独建模

一个造课任务可能调用模型几十秒，但用户可能明天才确认课程方向。如果把“等用户点击”写成worker中的等待，唯一执行槽就被占住，其他课程和课堂问答都无法执行；进程重启还会丢失这次等待。

正确拆法是：模型保存规划后结束本次执行，将run置为`awaiting_blueprint`。此时“任务未完成”与“worker正在工作”不是一回事。用户确认是另一条显式命令，提交后才重新入队。

```text
生成蓝图 ──保存──→ awaiting_blueprint        worker已空闲
                         │
              用户提交带版本的批准命令
                         ↓
                 generating / units ──入队──→ 单元1 → 单元2
```

## 三个不能混用的版本

| 标识 | 解决的问题 |
| --- | --- |
| run.version | 用户操作的是不是当前运行状态？取消、确认、调整都要乐观锁 |
| course.version | 新到的课程GET是否比当前页面快照更新？单元提交与学习事实也可能提升它 |
| blueprint_version | 用户批准的究竟是哪一版规划？展开必须绑定它，不能只判断“有课程” |

课程还有`creation_run_id`指向当前生成者。显式重试虽然沿用course_id，却换了run_id；父运行的晚到响应不能继续改这份课程。

## 队列去重的反直觉陷阱

队列通常用`(run_id, stage)`去重。但蓝图生成保存完成后，通知浏览器的异步间隙里，用户可能立刻提交修改意见：

1. worker尚未释放原`blueprint`去重键。
2. 修改命令已将数据库改为`generating / blueprint`。
3. API重新入队被原键去重。
4. worker根据之前的`awaiting_blueprint`快照判断无需继续，任务就永远停了。

因此收尾要**先移除当前去重键，再读取最新已提交状态**。已提交的生成流程才能自动续行；失败的网络请求仍要用户显式重试，不能拿这段逻辑做无限收费重试。读取遇到短暂数据库锁时，只重试读取，不重做已经成功的模型调用或单元提交。

## 前端也不要把一次请求当成确认事实

“某次reload的Promise成功”不是稳定的业务条件。第一次读取失败后，后续轮询可能已经恢复；如果只记住第一次结果，页面会显示正确内容但按钮永远禁用。

确认门禁应跟随当前持久快照：run在等待、蓝图版本相同、课程仍为blueprint，且creation_run_id属于当前run。这样任意一次成功的权威读取都能恢复操作；服务器仍以expected_version做最终校验。

## 自检

- 等用户一小时，是否有模型线程／worker一直被占用？
- 已确认规划能否被旧标签、旧run或迟到响应替换？
- 一次读取失败后自动同步成功，用户是否还必须刷新整页才能确认？
- 连续同阶段工作是否可能在解除去重之前再次入队并丢失？
