# 评测要记录事实，而不只记录承诺

一次评测至少有三种不同的信息：**配置要求系统做什么、运行时实际发生什么、判定者据此得出什么结论**。把它们混在一起，就容易产生“配置了上限所以费用受控”“工具成功所以业务成功”“模型说通过所以质量很好”的错觉。

## 请求上限不等于实际使用量

OpenAI-compatible只说明部分协议兼容，不代表每个参数都被供应商执行。例如官方DeepSeek的[Chat Completions文档](https://api-docs.deepseek.com/api/create-chat-completion)声明max_tokens；使用别家字段max_completion_tokens，不能据此宣称限额已生效。

因此同时记录请求参数、实际usage和预算审计。上限字段修正后，纯函数测试只能证明请求会构造成正确字段，不能证明远端一定遵守；必须把尚未执行的真实复验明确留空。供应商未返回usage时保留unknown，而不是补零。推理token的计费元数据与隐藏推理文本也不是一回事，不为解释成本而采集隐藏思维链。

文档核对日期为2026-10-26，供应商文档会变化，字段适用范围不能无条件推广到所有代理端点。

## 执行身份与评分身份不同

Case描述任务，一次execution产生业务事实，一次grading attempt对固定事实作判断。同一道题的good和bad是不同运行样本，不是两道重复题；重评也不是重新执行。

```text
Case → execution A → grading 1
                  → grading 2（重用同一回复和证据）
     → execution B → grading 1（重新调用业务）
```

恢复时先查询已保存的命令／run。回执消失可能意味着结果未知或数据库回滚，不能直接换身份重发；当前turn指向retry产生的新run，也不能冒充原执行。未评分占位在首次评分后应被替换，不能把它再算作一次运行。

## 结构有效与内容正确不同

ATIF校验只说明轨迹符合当前出口约束，不能证明没有源端漏记录或数学解释正确。LLM Grader返回合法JSON，也只证明输出可读取；其引用、适用性和结论仍可能有错。保留原始评分，再单独记录复核意见，不覆盖原判定来制造“一致”。

三个自检问题：这次重出报告会不会再调用模型？这个good标签对应一道题还是一次运行？所谓预算通过来自请求配置还是实际usage？如果回答不清楚，应先补证据身份，而不是增加自动化层数。

本轮实践及边界见[执行计划](../../exec-plans/completed/20261026-lightweight-backend-eval.md)。

## 修复当前规则，不改写历史事实

“不要A、B、C”中的否定作用域不是固定长度的前缀。若产物种类来自闭合词表，可以只在明确的并列连接符间传播否定，遇分句重置；这是可解释的局部修复，不能推广为任意语义理解。

由此派生的请求/禁止类型一旦进入run输入快照，就成了那次执行事实。修复解析器不应回写历史失败run；按快照重试与用新规则创建新执行也不同。局部SQLite回归能证明新规则不再错误要求产物，不能证明修复后模型会给出恰当的提示。

真实模型复验还可能同时得到“课程结构ready”“官方正文抓取失败”“浏览器能渲染图解”“移动端溢出”四个结论。分别报告这些事实，比改一个总passed或重跑到成功更有诊断价值。实例及原始证据入口见[复验计划](../../exec-plans/completed/20261026-real-teaching-refactor-validation.md)。

## 预算实验与失败诊断

控制变量应核对首个真实请求的system_prompt、messages、tools及模型，而不只复用用户最后一句话；历史和派生输入也会影响输出。2026-10-26动画单样本在完全一致的首请求上下文下把预留提高到16384，仍产生用满上限的未闭合工具JSON；不能因此继续加额、声称成功，或推导某个Skill是必需品。

失败时若适配层先解析tool arguments、再读取finish_reason，解析异常会丢掉两类关键证据：尚未闭合的生成内容、供应商实际结束标记。规范化error和usage只能证明错误及用量，不足以分析重复输出或精确截断原因。应先完善限长脱敏诊断，再考虑新付费实验；不能为补日志自动重跑失败样本。无成品时浏览器检查应标未执行，不用官网样例或手写HTML替代本次生成结果。实例及边界见[预算实验](../../exec-plans/completed/20261026-animation-output-budget.md)。
