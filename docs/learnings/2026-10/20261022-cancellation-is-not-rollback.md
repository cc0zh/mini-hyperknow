# 取消请求，不等于撤销外部调用

点击“取消”至少涉及三个不同事实：界面不再等待、业务结果不得生效、外部服务是否停止计费。它们不能用同一个 cancelled 标志混为一谈。

## 为什么取消 await 不够

同步 SDK 放入 asyncio.to_thread 后，取消等待它的协程通常不会杀死线程，更不能证明服务端请求已经停止。如果立即释放执行槽并启动下一次调用，界面虽然只显示一个任务，真实模型可能已经并发执行。

因此执行槽绑定实际同步调用的生命周期，直到调用返回或超时。用户取消仅能可靠撤销本地结果的提交资格，已发出的远端调用仍可能产生费用。

## 两道门禁解决不同问题

| 门禁 | 检查位置 | 能保证什么 |
| --- | --- | --- |
| 调用准入 | 每次首次／修复调用前检查持久化状态与线程安全停服信号 | 已确认取消或停服时不主动追加后续调用 |
| 提交屏障 | 在保存课程的同一个数据库事务中重查生成状态 | 取消后的晚到响应不能创建课程或覆盖状态 |

只有提交屏障，仍可能在用户取消后发起收费的结构修复；只有调用准入，仍可能把取消前已发出的晚到结果存入数据库。两道门禁都必要。

状态检查与网络发包无法组成跨服务的原子事务；调用刚准入的边界仍应视作在途请求，不承诺绝对零取消费用。UI 应诚实说明这一点。

## 重启为什么不自动恢复收费工作

数据库保存 queued、generating，不代表进程重启后应自动再次发送请求。旧请求可能已经在远端成功，只是本地没有收到结果；自动补发会重复收费。

保守做法是把未终结运行标为 interrupted，由用户显式重试产生新 run，保留父运行引用。等待澄清和已保存的结果不需要重做。

## 如何验证而不替换依赖

直接用真实 SQLite 验证取消状态禁止提交、重复完成最多一个课程、重启标记和调用门禁；这证明本地规则，不证明真实 SDK 的取消时序或远端计费。后者必须另用真实模型调用观察，缺凭据时明确 blocked。

自检：取消后结构错误还能进入修复循环吗？原调用未结束时是否已经释放执行槽？通知失败能否影响已提交数据？这些问题比只断言页面显示“已取消”更重要。
