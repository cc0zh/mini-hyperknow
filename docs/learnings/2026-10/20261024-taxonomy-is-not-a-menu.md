# 分类法不是菜单

内部枚举一旦出现在界面上，用户就被要求先回答一个自己没在问的问题。即时协助原本让学习者选「本轮操作：提问／闪卡／测验／白板／动画」，等于要求他在看到讲解之前就决定要什么形式。真实产品的做法是让他只说问题，形式由模型按内容判断。

## 为什么删掉下拉比改语义更难

删掉 UI 很容易，难的是删掉的枚举原本承担着一条可靠性属性。当客户端声明 `action=flashcards` 时，服务端可以强制「必须有 flashcard 产物，否则整轮失败」，这是**用户明确要求 → 必须兑现**的硬保证。枚举消失后，这条保证就没有触发条件了。

如果直接降级为提示词期望，用户说「给我做几张闪卡」，模型没调工具也不算失败，只是这一轮空手而归。这条属性就悄悄丢了，而且在测试里看不出来，因为测试通常只断言成功路径。

## 把声明变成派生

折中做法是保留硬保证，但把触发条件从「客户端声明的枚举」换成「从用户自己的话里派生」。同一段文本既驱动教学，也驱动保证：

- 点名的类型 → 必须创建，且只能是这一种；
- 明确拒绝的类型 → 不得创建；
- 都不命中 → 模型自由决定，可以不产出。

请求与拒绝必须**分开建模**。「没有点名」和「明确拒绝」在空列表里无法区分，而真实模型正是在第二种情况下犯了错：学习者说「只解释当前白板，不生成新白板」，模型却新建了一块。空列表只表达「不强制」，所以拒绝必须单独一个字段，并在工具层与提交层各强制一次。

## 启发式的边界要写下来

关键词判定一定会误判。第一次真实运行就撞上了：「解释**当前白板**第一步」被认为是新建白板请求，整轮以结构错误失败。修复不是加更多正则，而是承认这类措辞在**指代已有产物**，用前文参照词（当前／这块／上面的…）抑制命中，并补一条以真实失败原句为输入的回归。

这类判定永远是近似。写清它读什么、不读什么，比宣称「已理解用户意图」诚实得多。若将来需要真正的多数并列、否定嵌套与中英混写，应当换成分类器，而不是继续堆关键词。

## 自检

1. 删掉某个界面枚举后，原先由它触发的服务端强校验是否还有替代触发条件？
2. 「没有要求」与「明确拒绝」在你的数据结构里能区分吗？
3. 启发式判定的失败是否以显式错误暴露，而不是静默降级为「这一轮没产物」？
