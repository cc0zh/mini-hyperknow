# 一个版本必须对应同一个权威快照

## 问题：只改读取结果，也可能破坏一致性

客户端常用 `incoming.version > current.version` 合并新快照。这个规则成立的前提是：同一资源、同一版本，返回的权威事实相同。

假设保存接口返回 `version=8, play_intent=playing`，GET为了“刷新后暂停”，不改库却返回 `version=8, play_intent=paused`。两份快照都合法吗？不是。客户端无法判断哪份更新：允许同版本覆盖会受响应顺序影响；拒绝同版本覆盖又无法得到期望值。修正合并器不能弥补服务端破坏的版本语义。

## 把恢复策略与保存事实分开

- 服务端GET、写入响应、幂等重放返回同一权威播放意图，不做静默变换。
- 客户端重建播放器时创建暂停时钟；读到历史playing不等于收到播放命令。
- 只有用户明确播放／继续才启动本地时钟；断网后晚到的保存结果也不能擅自重启它。
- 会改变整个课堂快照的问答事实，需要课堂顶层version；progress.version只管理进度命令冲突，不能拦住“位置没变但答案更新”的快照。

因此“保存了什么”和“恢复后现在做什么”不是同一个状态。把两者混在一起，才会需要无止境地给GET、重连、定时器打补丁。

## 如何自检

1. 同一写命令的响应、随后GET及同身份重放，在同版本下是否一致？
2. 一个旧GET在新答案之后返回，会不会把互动列表覆盖回去？
3. 页面刷新、断网重连、晚到PUT，是否都不会自动启动时钟？

这三类检查分别约束协议、聚合版本和客户端副作用，不需要伪造模型。真实数据库和本地HTTP能验证前两类，直接时钟逻辑及真实浏览器验证第三类。来源见[本次实现](../../histories/2026-10/20261022-1823-real-whiteboard-classroom.md)。
