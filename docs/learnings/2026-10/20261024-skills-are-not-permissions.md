# Skill 提供方法，不授予能力

一个会讲解的 Agent 至少有三个不同层次：**Skill 决定怎么教，Tool 决定能做什么，业务代码决定什么算已完成**。把三者都放进提示词，通常会得到一个能声称成功、却无法可靠恢复的聊天机器人。

## 为什么分开

例如“概念讲解”需要先判断基础、选择例子、检查理解。这是教学方法，适合写成 Skill。生成闪卡需要结构化问题／答案，可以成为 Tool。但闪卡属于哪个会话、取消后是否还能保存、失败是否留下半个产物，不能由模型自己决定，必须由服务端事务约束。

因此，读到了写有“请运行命令”的 Skill，并不代表 Agent 获得命令权限。真正的能力来自宿主注册的工具集合；产品教学 Agent 只得到五个受控工具，开发助手即使能访问整个工作区，也不应把这种权限继承给产品。

## 渐进披露与重试快照

初始上下文只放名称和适用条件，模型选中后才加载正文。这不仅减少提示长度，也使实际选择可以追溯。不过“按需读当前文件”还不够：今天失败、明天改了 Skill，再按原请求重试，行为依据就悄悄变了。

做法是在创建业务 run 时固定版本、正文和摘要，初始仅从快照公开目录；工具激活仍读取这个快照。重试沿用原快照，新请求才采用新文件。摘要能检测意外变化，**不能把不可信正文变成可信权限**。

## 产物暂存不等于完成

工具成功可以只意味着“内容已经校验并暂存在本轮”。最终回复、所有产物和run ready必须在同一业务事务提交。每次调用前检查取消，提交前再次检查；同步网络取消不保证供应商停止，晚到响应只能进入审计，不能重新把会话变成完成。

类似地，保存了测验题目不等于保存了用户选择，保存了HTML不等于保存了动画运行现场。持久事实与浏览器临时状态分开，恢复语义才不会靠猜。

## 自检

1. 去掉某个 Skill 后，工具权限是否仍由同一注册表决定？若不是，方法和权限混在了一起。
2. Skill 文件修改后，失败请求重试能否还原当时依据？
3. 取消发生在最后一次网络请求之后，数据库是否仍能拒绝晚到产物？
