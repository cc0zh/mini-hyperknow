# 为什么删除内容后还要保留命令回执

删除接口最难的不是 `DELETE FROM`，而是客户端不知道它是否成功的那一刻。

设想服务器提交删除后网络断开。用户看到错误并刷新：课程已经不在列表里，但原请求是否成功没有被确认。如果重试只按课程是否存在判断，就会返回 404，客户端无法区分“刚才成功删除”与“从未找到课程”。如果误改成创建或使用新命令，还可能操作错误对象。

## 把数据寿命和命令寿命分开

- **业务数据**随课程删除：讲义、进度、练习、关联运行等，在同一事务内一起清理。
- **命令回执**保留最小身份及输入摘要：相同命令、相同输入重试时返回已完成删除的确认；不同输入复用同一编号则拒绝。
- **旧创建回执**不能复活已删除对象：保留身份不等于保留恢复能力。重放读取不到资源时，明确返回 404。

因此，一个新删除请求按“检查回执 → 检查版本和活动任务 → 删除关联数据 → 写成功回执 → 提交”执行。回执也必须和删除在同一事务里：不能出现记录已删但成功凭据没保存的中间状态。

## 前端也要维护同一个身份

网络失败只表示结果未知，不表示服务端没有执行。客户端保留原路径、版本和命令编号；刷新后允许显式重试，而不是换版本或生成新命令。“保留课程”只适用于请求发送前，结果未知后只能说“稍后确认”，因为关闭弹窗无法撤销服务器上的事务。

页面也有寿命：旧页面的迟到响应不能清掉新页面保存的另一条命令。清理前比对命令编号与路径，并避免已卸载页面改写后来页面的状态。这个所有权检查与服务端幂等解决的是不同层次的问题，两者都需要。

## 自检

1. 删除成功但响应丢失，刷新后还能用原身份得到确定答案吗？
2. 删除中任意一个 SQL 失败，会完整回滚还是留下半门课程？
3. 用户离开再返回后，旧请求回包会误清掉新请求吗？
