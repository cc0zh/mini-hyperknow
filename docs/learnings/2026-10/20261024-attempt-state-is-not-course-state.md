# 一次尝试的失败，不等于资源现在仍失败

想象文件上传第一次超时，第二次成功：如果列表仍把第一次的错误当成文件状态，用户会再次上传。课程生成也是一样，`run.status` 描述一次尝试，不描述整门课程此刻是否可用。

## 分开两条时间线

- **尝试历史**：原任务失败，重试创建新任务，历史事实不可改写。
- **当前资源**：课程通过 `creation_run_id` 指向当前负责生成的任务。它成功后，课程入口应该展示当前任务，而非要求用户逐次排除旧失败。

因此不要把旧失败改成成功，也不要按相同目标文字合并：同名课程可能完全独立，运行的更新时间也未必代表课程拥有权。用保存的稳定身份决定入口，用 `parent_run_id` 追溯重试。

## 两个容易遗漏的边界

1. 列表只取最近 30 次运行，当前成功任务可能不在窗口里。仅从列表找“有没有成功重试”会漏判，必须结合课程上的当前拥有者。
2. 自动跳转不能破坏历史与未知命令恢复。普通链接进入最新任务，显式历史链接保留旧原因；有未确认写请求时先处理原命令，不能悄悄丢掉恢复入口。

课程快照和运行列表分开读取，也可能短暂看到“旧拥有者＋新重试”。已知祖先链能帮助保留更新的后代，但不能以失败历史覆盖已确认的资源身份。
