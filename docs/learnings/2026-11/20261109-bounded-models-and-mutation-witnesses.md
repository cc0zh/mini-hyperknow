# 小模型通过不等于产品已被证明

## 区分两个命题

TLC 检查的是一个状态模型。本次造课模型只有两个单元，每个单元的复杂教学内容被抽象为一次已校验的提交。检查全部可达状态，只能说明这个范围内的 ready 门禁没有反例。

Python 真实实现是否符合模型，是另一个命题。事务边界、函数分支或版本检查改了，旧模型仍然可能通过。因此每个技能记录实际源码符号、文件 SHA256 和核对时的基准提交。工作区有未提交改动时，提交号不能代表当时实际检查的代码。

## 用故障实验检查验证器

造课保存规则要求所有单元 ready。如果把 `all` 改为 `any`，第一个单元提交后就会过早宣布课程就绪。

同一个故障需要两种证据。

1. 模型变体必须违反 `ReadyRequiresAllUnits`，产生可读的最短路径。
2. 隔离副本中的真实源码变更必须使原数据库测试断言失败。恢复源码后，同一测试必须通过。

导入错误、解析失败或 Java 崩溃不是发现缺陷。检查入口必须区分这些失败类别，否则一个永远不能运行的检查也会显得有效。

## 让原子动作对应真实事务

`finish_unit` 同时提交单元结构、课程统计和 run 状态。模型把这些写入作为一个动作，因为另一个 SQLite 命令不能观察到事务中间值。

模型调用则发生在事务外。不能把网络请求与结果提交合成一个不可分动作，否则取消和迟到结果之间的竞争会被模型提前排除。当前六个性质没有穷尽这些并发场景，后续扩展应先明确哪些中间状态真实可见。
