# 区分空扩展字段和无效内容

## 为什么完整重试也会失败

模型可能生成一份教学内容完整的 JSON，同时附带 Schema 没有定义的空备注。`extra=forbid` 会拒绝这份结果。要求模型重写整篇内容时，下一次可能增加另一个空备注，或在重复输出长报告时被截断。增加输出上限不能消除最初的结构错误。

本次真实反例包括 `project_stages=[]`、`sessions_note=null` 和 `evidence_note=""`。它们出现在不接受这些字段的嵌套对象中。只移除这些空扩展字段，原有课程或报告即可通过完整校验，不必重新生成知识和证据。

## 在输入边界做有限处理

先使用真实 Schema 校验。仅当全部错误都是 `extra_forbidden`，且每个错误值都是 null 或精确空的字符串、列表、对象时，复制输入，按错误路径移除字段，再使用同一 Schema 校验。领域对象内部不增加宽容分支。

这个顺序保留 Schema 作为唯一字段来源。它不需要手工维护允许忽略的字段名，也不把 `extra=ignore` 扩散到所有未知内容。原始模型响应仍用于审计，规范化不能原地改写它。

## 哪些情况不能忽略

- 已知字段的空值仍受原有约束。空 `sessions` 不能变成合法单元。
- 0 和 false 不是空数据。含空格的字符串也不是精确空字符串。
- 非空的未知项目阶段不能直接删除。它可能是放错位置的真实教学内容。
- 缺字段、类型错误和未知字段同时出现时，仍交给完整修复流程。
- 引用存在和逐字匹配仍须校验。格式通过不证明网页语义支持主张。
- 报告遗漏工具已经使用的问题 ID 是契约错误，不是空扩展字段。修复请求必须提供缺失的 ID，不能只给笼统的“引用无效”。

## 怎样证明没有吞错

同时测试三个方向。合法内容及原始输入不变。真实的空扩展反例通过。非空扩展、缺失课时、越权引用及不匹配的批准项目仍失败。直接校验已保存响应只证明边界行为，真实模型、事务保存和浏览器恢复须另行验收。
