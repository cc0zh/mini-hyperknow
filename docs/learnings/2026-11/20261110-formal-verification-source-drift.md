# 通过的模型为什么仍可能遗漏产品缺陷

形式检查验证的是给它的描述。当前代码多了一个写入口，旧模型仍可能通过，因为新入口根本没有进入它的状态空间。先问模型描述了谁，再问性质是否通过。

## 把源码快照和提交分开

sync_commit用于定位需要审阅的历史，不等于执行快照。记录时若存在未提交代码，还需要文件摘要。本次旧runtime摘要匹配后续提交，说明当时已验证过那段实现。直接按基线提交差异判断，会把旧行为误认成新增变化。

先找旧摘要对应的实际内容，再审阅新写入口是否触及同一字段。不能只刷新摘要来消除门禁报错。

## 保留性质，把新缺陷单独验证

脚本式课堂要求先确认最后总结再完成。新增teacher任务没有有意取消这个承诺，因此Summary性质不变。模型补回了首次确认前允许提问的路径。

真实SQLite重放另一个路径时，新teacher任务遮蔽了活跃再生成，导致旧脚本问题被接受，替换脚本后又从当前列表消失。这个缺陷与Summary性质不同，不能拿旧模型通过来否定它，也不能修改Summary性质来掩盖它。独立探针让这个缺陷有自己的失败结果。

## 通过后再确认检查仍有能力失败

把守卫在临时真实源码副本中禁用。基线应通过，变体应以目标断言失败，恢复后再通过。导入失败或解析错误不能算捕获缺陷。0、1、0能证明这次检查对指定错误敏感，仍不能证明模型覆盖所有协议。

下次看到一个通过结果，先检查三个事实。它对应哪份源码，它穷举了哪些动作，哪一种真实错误能让它失败。复现和本次局限见[维护记录](../../exec-plans/completed/20261110-maintain-formal-verification.md)。
