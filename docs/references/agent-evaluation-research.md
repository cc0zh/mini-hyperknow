# mini-hyperknow：Agent／教学 eval 论文调研与建议

调研日期：2026-10-25。状态：外部研究与候选设计建议；用户已授权留痕，尚未授权据此实施。

关联：[产品范围](../design-docs/product-design.md)、[即时协助契约](../design-docs/instant-assistance.md)、[真实验收](../design-docs/real-validation.md)。论文结论、工程建议和仓库事实分别标明；本文不改变产品契约、架构约束或质量状态。

## 建议

以有明确目标、初始状态与可观察结果的教学任务组织 eval；任务是运行／比较单位，回合是观察单位，检查项是判定单位。能力覆盖从产品承诺向下推导，具体检查项从真实输出和失败向上校准，同时主动补入真实日志没有覆盖的边界案例。工程检查、教学场景评测和真实端到端验收继续承担各自职责。

当前优先做一个可运行、可比较、可追溯的轻量评测闭环；保留 SubjectAdapter 与 Grader 两个显式扩展边界。这里的“可插拔”是可替换真实执行对象与判定策略，不要求插件发现、热加载、依赖容器或通用评测平台。

被测对象、case粒度和判定粒度分别决定：可以替换一个Skill版本或整套Agent配置，仍以同一教学任务测其表现，再用更细的检查项解释变化。DeepSeek借鉴显式装配与替换边界，Comet借鉴配置快照、证据闭环和配对比较；教学标准用本项目案例校准，不直接搬入通用Agent总分。

## 项目实现核对与真实种子

以下是调研时的仓库事实，后续实现变动需重新核对：

- [真实调用记录与Skill执行](../../src/hyperknow/assistance_generation.py)：记录输入、响应、实际usage及Skill元数据；现有契约要求加载Skill。格式修复也是实际调用，成本计入同一任务。
- [即时协助提交](../../src/hyperknow/assistance_storage.py)：工具先暂存草稿，最终回复与产物在事务中提交；评价保存结果时不能只看工具返回。
- [Agent事件](../../src/agent_core/engine.py)：观察回调失败只告警，不中止运行，事件不是唯一权威证据。
- [用量统计](../../src/agent_core/tokens.py)：未知usage与已知部分和分开，输入预算估算不能当实测用量。
- [现有生成入口](../../src/hyperknow/generation.py)、[真实协助验收脚本](../../scripts/verify_assistance.py)：课程、讲义、问答、测验和即时协助已有执行路径；新增eval不应重写执行内核，也不能替代真实业务验收。
- [即时协助内容边界](../exec-plans/completed/20261024-instant-assistance.md#内容与未覆盖边界)记录有限差商表述缺条件、两步意图扩展成六步；[教学内容债务](../exec-plans/tech-debt-tracker.md)记录摄影题组继承讲义错误、课程预计435分钟超过需求420分钟。保留原始生成事实，用作回归种子，不手改产物冒充模型已改进。

## 研究结论与取舍

1. “任务级为主”不意味着每任务只给一个总分。TeachArena的多轮内部还区分回合、轨迹、学习者表现；17个模型在判断与多轮、多轮与工作流的描述性排名相关仅约0.24、0.21（§4，表6）。这些结果支持分项报告，不能据单轮成绩推断系统教学表现。
2. 首批要包含讲义／测验生成。TeachArena读取83个材料生成／修改任务的持久化内容，文件存在不是充分条件（表5）。本项目已有“测验忠于错误讲义”的真实案例，应把来源忠实与事实正确分别检查。
3. top-down与bottom-up承担不同工作，没有论文证明其中一种适合作为整个eval的唯一方向。前者界定目标和覆盖；后者让判据具体可用。主动压力案例补充真实日志的遗漏。
4. 不照搬41项量表、Attune完整优化管线、学生模拟训练或自动evaluator自我迭代。先校准少量与本项目行为相关的判据。
5. 不要求单人项目建立四套独立数据管线或五专家评审。开发场景与未参与调规则的留出场景先分开；回归是场景标签，人工锚点是用于校准判定的真实输出样本。
6. AgentSuite提醒先检查题面、参考与评分是否正确：规定唯一工具序列可能惩罚有效替代方案，过宽判定可能奖励无作为。其平衡子集F1约0.791–0.874，全量人工复核主要针对标记项，不能宣称自动审计清除了所有缺陷（§4.1–4.2）。

## 建议的评测结构

### 被测对象

三个粒度分别定义，避免把被测组件、运行单位和判定单位混为一谈。

| 层面 | 定义 | 示例 |
| --- | --- | --- |
| 被测对象 | 本次比较的配置或组件 | 模型、Prompt、Skill版本、Agent／Harness配置 |
| 运行与比较单位 | 有目标、初态和结束条件的任务 | 解释误区、短多轮辅导、生成测验 |
| 判定单位 | 一条有证据位置的具体要求 | 数学条件正确、等待continue、产物保存 |

被测对象是一套配置明确、可实际执行的系统：模型＋prompt／Skill快照＋工具与执行器＋上下文策略。实验必须声明改的是哪个因素。

- 比较模型：其余配置固定。
- 比较prompt／Skill：尽量固定模型、输入、工具和预算。
- 比较Harness：固定任务和模型，记录上下文、工具、重试、预算等差异。
- 产品版本整体比较：允许多个因素变化，但结论仅归于整体版本，不强行做单组件归因。

当前即时协助要求加载Skill，因此“直接关闭Skill”会违反产品契约；比较两个均符合契约的Skill版本更公平。

### Case

每个case至少包含：稳定ID／版本、能力与风险标签、真实执行入口、用户目标／误区、初始上下文与来源、用户输入或有限分支、停止条件、预算，以及检查项。每个检查项写明适用条件、判定标准、证据位置和grader类型。

原子检查项的结果为通过／失败／待判；不适用项单独标记，不能算通过。缺证据、judge失败、内容截断和确实违反要求要分开记录。条件允许时保留解释和原文引用。允许不同正确解法，不把特定措辞或非必要工具顺序写成唯一答案。

示例case：“用户会基本求导，但不理解复合函数为什么要乘内层导数；要求分两步讲，第一步结束后等continue。”运行单位是完整短教学片段；观察点包括澄清、第一步、continue后的衔接；检查项分别验证解释的数学条件、教学深度、等待／计划一致性与最终保存状态。用户要求的是提示还是完整解法属于case目标，不制定一律禁止给答案的通用规则。

### 第一批覆盖面

| 任务族 | 优先覆盖的可观察行为 |
| --- | --- |
| 内容生成 | 蓝图与需求／时间对齐；讲义事实与条件正确；题干、答案、解析一致；题目既忠于来源又不继承事实错误 |
| 当前上下文问答 | 使用已展示内容，诊断用户具体误区；提示请求不直接泄露答案；用户要求完整解法时允许直接回答 |
| 短多轮辅导 | 澄清后计划不擅自膨胀；显式continue衔接；重复错误后改变解释；正确答案但理由错误时仍能诊断 |
| Skill与产物 | 合理选择／加载Skill；遵守用户产物意图；保存的闪卡／题目／图／白板／动画内容与目标一致 |

这四类不是四个独立平台。一个case可以覆盖多个检查点。保存恢复、取消和幂等继续由相关工程检查与少量真实全链路门槛覆盖。

### 最小框架

Case → SubjectAdapter调用现有真实路径 → EvidenceBundle → Grader → Report。

只为SubjectAdapter和Grader保留显式注册／替换点，Case、EvidenceBundle、RunRecord作为普通版本化数据即可。复用现有provider、工具和worker，评测器不重写一套Agent循环。

证据包至少包括：case与subject快照、run状态／错误、实际输入与相关上下文、保存后的回复／生成物、实际模型调用记录与usage、相关业务前后状态。SQLite继续保存业务事实；评测结果外置记录。工具返回“已创建”只是暂存成功，必须核对最终事务提交的产物。

AgentEvent回调失败不会中止执行，不能只靠事件流证明业务完成。未知usage保留未知，估算token预算不能冒充实测用量或费用。

### Grader与人工校准

先用确定性检查验证明确的结构、状态、范围、引用身份和可计算结论；这些检查本身不能证明教学内容正确。开放式教学判断交给少量任务相关的原子rubric，优先单条评判，并用本项目中文真实输出校准。批量多条判据是否省钱且可靠要实测，不能从其他领域直接照搬阈值。

从成功、部分满足、失败、条件缺失、证据不足等样本建立人工锚点；人先判断，再检查judge是否把部分满足误判为通过或额外添加要求。人工与judge不一致时先检查判据和证据，而非立即换模型投票。单人复核不声称多人一致性，复杂知识错误必要时查权威资料。

A/B偏好比较可用于发现遗漏标准；它不能替代绝对正确性检查，因为“B优于A”仍可能是两者都错。

### 比较与报告

固定case、初始上下文、评测器版本和预算，baseline／candidate隔离真实数据库与副作用，按照case ID＋版本／hash＋重复编号配对。相同case不意味着外部网页内容永远不变；检索任务记录时间和实际来源，把环境变化列为限制。

起步可安排约20–30个任务，以多数开发场景加少量留出场景组成；这是可承担的工程起点，不是论文证明的统计充分样本量。人工锚点可来自开发任务的真实产物。首次先验证流程，有改善信号后再对易波动任务安排两边等量重复；不从一次小样本结果宣称显著胜出。

留出场景在调整规则时不使用；看过失败并据此改动后，应将该场景视为已暴露，并另补新留出题。历史真实失败保留回归标签，不因不利结果移除。

报告至少分开列出：执行成功／异常，关键契约失败，内容和教学行为检查，待判／缺证据比例，实际调用／usage／耗时与可核算费用。保留全体计划任务作为报告范围，不静默删除失败任务或只比两边成功的子集。分任务族汇总，避免多轮任务因检查项多而自动获得更大权重；必要时另给配对子集分析并说明缺失。

## 推荐落地顺序

1. 从仓库已有真实失败和产品契约挑选少量任务，人工写出“目标—证据—检查”链；包括有限差商条件、两步计划膨胀、摄影讲义／测验共同错误、课程时间预算等。
2. 先实现一个现有入口的SubjectAdapter，把真实产物和证据收齐；先人工判定打通流程。保存历史产物的复核只用于grader开发，不冒充重新执行当前系统。
3. 用中文真实样本校准少量开放式grader，再加入第二个版本做配对比较；固定数据和判据后才看留出结果。
4. 有稳定信号后扩展其他生成入口与少量完整学习链路。真实用户的前后测、迁移和延迟测验属于以后独立研究，不是当前作品完成条件。

当前最值得展示的证据是：一次可追溯的版本修改，在相同任务与预算下减少了某类真实教学失败，其他契约没有被高分掩盖，成本和未验证项清楚可见。
